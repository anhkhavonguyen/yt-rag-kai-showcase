# Spec Delta

## Purpose

Defines how the application is deployed to a free public host from the repository. Deploys cost nothing, ship only code that passed CI, and never put secrets in the repository.

## ADDED Requirements

### Requirement: Repository defines a free-plan web service built from the Dockerfile
The repository SHALL contain a deployment blueprint that defines exactly one web service on Render's free plan, built from the repository's Dockerfile, so that an owner with no payment method can create the service.

#### Scenario: Creating the service from the blueprint
- **WHEN** the owner creates a Render Blueprint from the repository
- **THEN** a single web service is proposed on the `free` plan, built from `./Dockerfile`, and creating it requires no paid plan

### Requirement: Deploys happen only after CI passes on main
The deployed service SHALL track the `main` branch and deploy a commit only after all of that commit's CI checks pass.

#### Scenario: Green commit on main
- **WHEN** a commit is pushed to `main` and its `lint`, `test` and `docker-build` checks pass
- **THEN** the service deploys that commit

#### Scenario: Red commit on main
- **WHEN** a commit is pushed to `main` and any of its CI checks fail
- **THEN** that commit is not deployed and the previously deployed version keeps serving

### Requirement: Service listens on the platform-assigned port
The container SHALL accept HTTP traffic on host `0.0.0.0` at the port given in the `PORT` environment variable.

#### Scenario: Platform assigns a port
- **GIVEN** the platform sets `PORT=10000`
- **WHEN** the container starts
- **THEN** the application serves HTTP on `0.0.0.0:10000`

### Requirement: Health check gates each deploy
The deployed service SHALL use `/healthz` as its health check, so a new deploy goes live only after `/healthz` responds successfully.

#### Scenario: Application fails to start
- **WHEN** a new deploy's container cannot start, for example because a required setting is missing
- **THEN** the health check never succeeds, the deploy is not made live, and the previous version keeps serving

### Requirement: Secrets are never stored in the repository
The blueprint and the rest of the repository MUST NOT contain secret values. The Supabase keys and the model API key SHALL be entered in the hosting dashboard, and the admin seed token SHALL be generated by the hosting platform.

#### Scenario: Blueprint contents
- **WHEN** the blueprint is inspected
- **THEN** `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` and `OPENAI_API_KEY` have no values (the dashboard prompts for them), `SEED_TOKEN` is generated by the platform, and only non-secret settings carry values

### Requirement: Blueprint defaults to the free model provider
The blueprint SHALL set the non-secret model settings to Google Gemini's free-tier OpenAI-compatible endpoint, chat model and embedding model. With only the secret values filled in, the deployed service answers questions with no further configuration.

#### Scenario: First deploy with a Gemini key
- **GIVEN** the owner entered a Gemini API key and the Supabase credentials, and the Supabase schema from `sql/init_supabase.sql` is applied
- **WHEN** the owner seeds the default documents with the admin token and then asks a question on the deployed URL
- **THEN** the question is answered using Gemini, with `debug.answer_mode` of `generated` or `extractive`

### Requirement: Free deployment setup is documented
The project documentation SHALL describe, step by step, how to get the free accounts and keys needed (Gemini API key, Supabase project and schema, Render blueprint), and how to find and use the generated admin token.

#### Scenario: Owner follows the documentation from scratch
- **WHEN** someone with no prior setup follows the documented steps
- **THEN** they end with a running deployment and a seeded knowledge base without adding a payment method anywhere
